# Phase 3: Observer screen, run control and exports
Status: Stage: Done | Round: 1/3 | Updated: 2026-11-02 20:11

## For Tim
This phase builds the full watching screen, at no cost. At the top there's a bar with the clock, day and season, a Pause/Resume button, speed buttons, a spending warning and an "autosaved" note. The map is on the left. It now also shows buildings (and damaged ones), graves, and sick, hurt and sleeping marks. On the right are five tabs: Chats, Choice points, World history, Players and Spend. You start a game with `new` and watch it with a new `watch` command. P or the button pauses it and saves. The game also saves itself every 6 game hours. You can close the program and carry on later. If the program is killed mid-game, it rebuilds itself exactly from the last save. While a game runs, the laptop is kept from going to sleep. A new `export` command writes every table as CSV files (spreadsheet-style text files) for R. A `measures` command prints weekly figures: promises, help vs. harm, villager welfare and belief acts.
How the work is split: two builders. One builds everything behind the screen (saving, pausing, recovery, measures, export, commands). The other builds the screen itself. They agree up front on exactly what the screen reads and which buttons it may press.
From Codex we're taking: a strict rebuild check after a crash, graves taken from the event log, no change to the save format (Phase 2 games stay loadable), tabs you can page through so no line is ever hidden, the exact list of what counts as "help", how weeks are counted, and the spend total. You are approving the plan below.

It is emitted once per action, at that action's first successful effect for someone else: a gift transfer to the target; use_herb on another actor that improves its body; teach after the entry is added to the addressed player (overhearers don't count); build/build_shrine work, or repair that raises hp, on a structure owned by another player (target = owner). Failed actions, self-care, trade and guard emit none. A cancelled action that already helped keeps its one event. `PlayerDay` gains `villager_loyalty: float | None = None`: the mean loyalty of that player's living villagers at the day boundary (None when it has none). - LiveRun (A; storage/run_control.py): `LiveRun.open(config, path, keep_awake: KeepAwake | None = None) -> LiveRun` needs an existing db (error: `run '<name>' does not exist; create it with: uv run python main.py new <name> --players dummy`). It takes the RunLock, recovers, attaches and acquires keep-awake. It has `sim`, `db`, `recovery: RecoveryInfo`. `advance(real_seconds: float) -> int`: owed ticks = real_seconds * speed / seconds_per_tick + carried remainder. It runs whole ticks one by one until owed is spent or max_tick_work_ms is used, keeps the unspent debt, and returns 0 while paused. Also `run_ticks(n)`. `pause()`: stops after the current tick, saves a checkpoint (once per transition), releases keep-awake. `resume()`: re-acquires and resets the wall-time origin, so paused or asleep time makes no catch-up ticks. `toggle_pause()`, `flush()` (writes pending whole ticks), `close()` (checkpoint at the current tick, release, unlock, close db; safe twice; also in finally/atexit). Frame loop in cli.py: pump -> advance(dt) -> flush -> draw -> sleep the rest of 1/fps.
- Autosave (A; in Simulation): with a db attached, `Simulation.run` saves a checkpoint each time world.tick reaches a positive multiple of autosave_interval. Chunks end on those ticks, and chunking never changes events. Example: 0 -> 721 saves at 360 and 720; a pause at 417 saves 417 and the next autosave is still 720. `sim.last_autosave_tick`. Applies to headless --run, resume and watch. It adds no event and draws no RNG. `Simulation.spend_usd` is written to Snapshot.spend_usd at every save; on restore it is set to db.spend_total() (never snapshot plus ledger).
- Crash recovery (A; storage/recovery.py): `recover(db, assets=None) -> tuple[Simulation, RecoveryInfo]`, `RecoveryInfo(snapshot_tick, tail_events, end_tick)`. Steps: restore the latest snapshot; tail = the K events with id > last_event_id, the last at tick T_e. If K = 0, attach as already stored. Otherwise set `sim.replaying = True`, run to T_e (whole tick), and compare the regenerated events with the tail on (tick, type, payload_json). Any difference, a missing event, or an extra regenerated event at tick <= T_e (a tail that ends mid-tick) raises RecoveryError naming the first differing event id, and the db is left unchanged. Then attach with the K events marked stored (chats never written twice) and set `replaying = False`. Eventless committed minutes after T_e are simply re-run, with identical results. Phase 4 hook: while `sim.replaying` is True, the mind layer must take AI replies from stored ai_calls keyed by (tick, player_id, call order) and never make a call. This is documented on the attribute; nothing more is built now. Recovery replaces `_check_no_tail` in headless --run, resume, watch and view. Example: snapshot 360, tail committed through tick 417, killed during 418 -> recovered at 417; running on to 1000 gives exactly the uninterrupted log through 1000, with each chat once.
- `--crash-after-tick N` (A; hidden from --help; headless, resume, watch): after tick N the run flushes its pending whole ticks (no snapshot), then calls os._exit(3).
- RunLock (A; storage/runlock.py): `RunLock(db_path)` opens `<run dir>/run.lock` and takes an OS byte lock (msvcrt.locking LK_NBLCK on Windows, fcntl.flock elsewhere). The OS drops the lock when the process dies, so a killed run never leaves a stale lock. A second writer gets RunBusyError "run '<name>' is already open in another window". Used by watch, headless --run and resume; view and export don't lock.
- KeepAwake (A; storage/power.py): `KeepAwake(setter: Callable[[int], int] | None = None)`. The default is kernel32.SetThreadExecutionState on win32 and a no-op elsewhere. `acquire()` calls setter(0x80000001), `release()` calls setter(0x80000000), on the owning thread. Both are idempotent. `active: bool`; `ok: bool` (False when the setter returned 0).
- Weekly measures (A; measure/weekly.py): `game_week(tick, week_ticks) = max(0, tick - 1) // week_ticks + 1`; ticks 1 and 10080 give 1, 10081 gives 2. `weekly_measures(db, week_ticks) -> list[MeasureRow]`, `MeasureRow(week, measure, player, partner, kind, value: float | None, samples: int)`. Measures: promises_made / promises_kept / promises_broken (player = maker, partner = to, each in the week it happened, no rate); help (Helped: actor, target, kind); harm (harm: actor, victim, kind); villager_deaths / villager_departures (player = the leader in the event); villager_loyalty (the mean of that week's player_day.villager_loyalty; None with samples 0 when there is no sample); belief_actions (belief_act, kind). For every week 1..game_week(last event tick) and every player there is a total row (partner "", kind ""), with 0 when nothing happened. Breakdown rows exist only when > 0. Example: promise_made player_1 -> player_2 at tick 100 and promise_kept at tick 10100 give (1, promises_made, player_1, "", "", 1), (1, promises_made, player_1, player_2, "", 1), (1, promises_kept, player_1, "", "", 0), (2, promises_kept, player_1, "", "", 1), (2, promises_kept, player_1, player_2, "", 1). `main.py measures --run <run>` prints them as a table.
- Export (A; measure/export.py): `export_run(db_path, out_dir) -> dict[str, int]` (file name -> data rows). It runs in one read transaction on a read-only connection and writes `<table>.csv` for each of the 8 TABLES plus `weekly_measures.csv`: UTF-8 without BOM, newline="", csv.writer, a header of schema column names, rows in primary-key order, NULL as an empty field, JSON verbatim, files closed. An empty table gives a header only. A chat with a comma, a newline, Hebrew and quotes re-imports as one row. `main.py export --run <run> [--out DIR]` defaults to `runs/<run>/export/` and prints each file with its row count.
- CLI (A): `main.py watch --run <run>` opens the full Observer on a persisted run (LiveRun); closing the window saves and exits 0. `new`, `headless`, `resume`, `report` are unchanged except for autosave, lock and recovery. `view` keeps its flags and is read-only: with --run it works on RunDB.copy_to_memory (and recovers a tail there); without --run it uses RunDB.memory(). It draws the full Observer with MemoryControls. `--screenshot` runs the ticks, flushes, draws once and saves. The source db is never changed.
